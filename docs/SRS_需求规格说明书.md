## 0. 一句话定义

**AI-KM 不是文档网盘，是"给 AI 用的知识底座"。**

它的唯一成功标准是：公司的知识能被 AI 准确检索、准确调用、并且每一次调用都可溯源、可审计。文档存得漂亮但 AI 检索不到，等于零分。

## 1. 战略目标反推（Why 这个平台必须存在）

### 1.1 SG1 对平台的硬约束

| SG1 里程碑 | 时间节点 | 对平台的硬性要求 | 平台需求编号 |
|---|---|---|---|
| 分类标准与入库规范文档完成（含正反范例） | 8 月中 | 平台必须把"规范"变成**系统强制校验**，而不是靠人自觉。不合规文档进不来 | FR-3.4 元数据强校验 |
| 示范场景关联知识入库完成（高质量）+ 平台上线 | 8 月底 | 平台必须在 8 月底前**可用**，且支持政策库 / 项目库 / 客户问答三类首批知识 | FR-2 知识分类体系、NFR-可落地 |
| 全量初版知识资产入库完成 | 10 月中 | 必须支持**批量入库**与部门并行作业，不能一份份手工传 | FR-3.2 批量导入 |
| **AI 检索查询准确率 ≥ 90%** | 10 月底 | 这是最硬的技术指标。必须**内建评测集与自动打分**，否则"90%"无法证明 | FR-6 检索质量评测 |
| 全量高质量验证 + 持续更新机制 | 12 月底 | 必须有**知识生命周期管理**（复审提醒、过期下架、版本留痕） | FR-7 知识生命周期 |

### 1.2 SG2 对平台的硬约束

| SG2 里程碑 | 时间节点 | 对平台的硬性要求 | 平台需求编号 |
|---|---|---|---|
| 2 个 AI 场景上线（信息整理、政策解读辅助） | 9 月中 | 平台必须开放**标准 API**，让上层场景应用直接调用检索与问答能力 | FR-8 开放 API |
| AI 私有化部署启动 | 10 月底 | 模型层必须是**可插拔适配层**，从云 API 切私有化只改配置，不改代码 | NFR-可扩展、FR-9 模型适配 |
| 全流程 AI 改造完成：整理×3、报告×5、查询+50% | 12 月底 | 平台需提供**用量与效能统计**，证明"查询效率+50%"这类指标 | FR-10 效能度量看板 |
| 场景首月定位"内部试用验证" | 9 月 | 平台需支持**灰度**：按部门开放、按场景开关 | FR-1.4 权限与灰度 |

### 1.3 关键推论

> **推论 1**：SG2 的 9 月中场景上线依赖 SG1 的 8 月底知识入库。知识库是关键路径上的前置节点，平台延期 = 整个下半年战略延期。
>
> **推论 2**："检索准确率 ≥ 90%"必须是**平台自证**的能力。如果 10 月底靠人工抽样评估，既不可信也不可持续。因此评测能力是 P0 而非"锦上添花"。
>
> **推论 3**：质量策略"示范场景优先高质量、全量后置到 12 月"意味着平台必须支持**质量分级共存** —— 高质量已验证知识与待提质知识在同一库中，但检索时可区分权重、可标记可信度。

## 2. 系统范围

### 2.1 在范围内（本期交付）

- 知识资产的采集、解析、切片、向量化、入库
- 分类体系与元数据规范的系统化强制
- 混合检索（关键词 BM25 + 语义向量）
- 基于知识库的 AI 问答（RAG），带引用溯源
- 权限与密级管控（部门隔离 + 三级密级）
- 全链路审计日志
- 检索质量评测集与自动打分
- 知识资产盘点看板（对齐 SG1 进度追踪）
- 开放 REST API 供上层 AI 场景调用
- 知识生命周期管理（复审、过期、版本）

### 2.2 明确不在范围内（避免范围蔓延）

| 不做 | 原因 |
|---|---|
| 在线协同编辑（类腾讯文档） | 已有成熟工具，重复造轮子。平台只做"归档与调用"，编辑在源系统 |
| 复杂工作流审批引擎 | 本期只做"提交 → 审核 → 发布"单级审核，够用 |
| 移动 App | Web 响应式即可覆盖 |
| 全文 OCR（扫描件识别） | 二期能力。一期扫描件走"人工补充摘要"降级路径 |
| 多租户 SaaS 化 | 公司内部单租户，过度设计 |

### 3.3 数据可见性规则（三重过滤，检索前置执行）

```
可见文档集 = 已发布(status=published)
           ∩ (密级 ≤ 用户密级许可)
           ∩ (文档部门 ∈ 用户可见部门 ∪ 文档为全公司可见)
```

**密级三级**：
| 密级 | 代码 | 定义 | 可见范围 |
|---|---|---|---|
| 公开 | `public` | 可对外发布的内容（产品介绍、公开政策解读） | 全员 + API |
| 内部 | `internal` | 公司内部流通（项目文档、内部规范、客户 FAQ） | 全员（默认） |
| 机密 | `confidential` | 敏感商业信息（报价策略、客户合同、核心算法） | 显式授权用户 |

> **强约束**：机密文档**不进入** AI 问答的默认上下文，除非用户具备机密许可且显式开启"包含机密"开关。该开关的每次开启均记入审计日志。

**文档级细粒度权限（对象级 ACL，P 完整版补齐）**：在以上「全局规则」之上，每篇文档可独立设置可见模式：
- `inherit`（默认）：沿用上述「部门 + 密级 + 状态」全局规则；
- `restricted`（受限/私有）：仅 `doc_acl` 白名单中的主体可见/可编辑，同部门未授权用户**不再自动可见**（解决"私有文档被本部门其他人看到"的漏洞）；
- 创建人本人**始终**可见（含未发布草稿）；管理员/审核员仅受密级约束，不受 ACL 限制；
- ACL 授权分两档：`view`（仅看）、`view_edit`（可看可改）。

## 4. 知识分类体系（对应 SG1 首批核心知识）

### 4.1 一级分类（六大知识域）

| 编码 | 一级分类 | 说明 | SG1 优先级 |
|---|---|---|---|
| `POLICY` | 政策法规库 | 医药/器械集采政策、招投标法规、地方细则 | **P0（8月底）** |
| `PROJECT` | 项目知识库 | 项目方案、实施记录、复盘总结、交付物 | **P0（8月底）** |
| `CUSTOMER` | 客户与市场 | 常见客户问答、客户画像、竞品资料、行业分析 | **P0（8月底）** |
| `PRODUCT` | 产品与技术 | 产品手册、API 文档、技术方案、架构设计 | P1（9月） |
| `PROCESS` | 制度与流程 | 公司制度、SOP、模板、表单 | P1（9月） |
| `TRAINING` | 培训与沉淀 | 培训材料、经验分享、AI 使用案例（对接 SG2） | P2（10月） |

### 4.2 二级分类
由各域负责人在《知识分类标准与入库规范》中定义，平台支持配置化维护，不硬编码。

### 4.3 质量分级（支撑"先保全、再提质"策略）

| 等级 | 代码 | 含义 | 检索权重 | 达成时点 |
|---|---|---|---|---|
| 已验证高质量 | `verified` | 经审核员校验，元数据完整、内容准确、可直接供 AI 引用 | ×1.2 加权 | 示范场景 8 月底 |
| 常规 | `normal` | 元数据合规、内容未逐条校验 | ×1.0 | 10 月中全量 |
| 待提质 | `draft` | 仅完成入库，质量存疑 | ×0.8 降权，问答中标注"未验证" | 12 月前清零 |

## 5. 功能需求（FR）

### FR-1 认证与权限

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-1.1 | 账号密码登录，密码加盐哈希（PBKDF2-SHA256，≥200k 次迭代） | P0 | 数据库中不存明文/可逆密码 |
| FR-1.2 | 会话管理，支持超时登出（默认 8 小时） | P0 | 超时后访问受保护接口返回 401 |
| FR-1.3 | 五角色 RBAC，权限矩阵按 3.2 执行 | P0 | 越权访问返回 403 并记审计 |
| FR-1.4 | 部门隔离 + 密级过滤，检索前置生效 | P0 | 无权限文档**不出现在检索结果中**（非前端隐藏） |
| FR-1.5 | API Key 机制，供 SG2 上层场景调用，可单独吊销 | P1 | Key 吊销后立即失效 |
| FR-1.6 | 首次登录强制改密 | P1 | 默认密码不可长期使用 |

### FR-2 知识分类与元数据

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-2.1 | 支持 4.1 的六大一级分类，二级分类可配置 | P0 | 管理员可增删二级分类且不影响存量数据 |
| FR-2.2 | 元数据字段：标题、分类、部门、密级、责任人、生效日期、失效日期、来源、标签、质量等级、版本 | P0 | 全字段可检索、可筛选 |
| FR-2.3 | 必填字段强校验，缺失则拒绝入库并给出明确提示 | P0 | 缺任一必填项无法提交，提示指明具体字段 |
| FR-2.4 | 标签体系，支持自由标签 + 受控词表 | P1 | 标签可用于检索过滤 |

### FR-3 文档采集与入库

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-3.1 | 单文件上传，支持 docx / pdf / xlsx / md / txt / html | P0 | 六种格式均能正确提取文本 |
| FR-3.2 | 批量导入：ZIP 包或服务器目录扫描 + CSV 元数据清单 | P0 | 一次导入 ≥100 份文档，失败项单独列出不中断整批 |
| FR-3.3 | 文档解析保留标题层级结构，切片时携带上级标题作为上下文 | P0 | 切片文本包含"章节路径"前缀 |
| FR-3.4 | 入库前规范校验：必填元数据、文件大小、格式白名单、正文最小长度、重复检测（内容哈希） | P0 | 不合规文档拦截，返回具体原因码 |
| FR-3.5 | 入库状态机：`uploaded → parsing → parsed → pending_review → published / rejected` | P0 | 状态可见、异常可重试 |
| FR-3.6 | 解析失败降级：允许人工补充摘要后入库（应对扫描件） | P1 | 降级文档标记 `draft` 质量等级 |
| FR-3.7 | 异步处理，大文件不阻塞界面 | P1 | 上传后立即返回，后台处理，前端可查进度 |

### FR-4 检索

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-4.1 | 关键词检索（BM25，中文分词） | P0 | 中文查询召回正常，非"整句才能匹配" |
| FR-4.2 | 语义向量检索 | P0 | 同义表述可召回（如"集采新规"命中"带量采购管理办法"） |
| FR-4.3 | 混合检索，RRF 融合排序 | P0 | 混合结果准确率高于任一单路 |
| FR-4.4 | 结构化过滤：分类 / 部门 / 密级 / 时间范围 / 标签 / 质量等级 | P0 | 过滤条件可叠加 |
| FR-4.5 | 结果高亮命中片段 | P1 | 用户能一眼看出为何命中 |
| FR-4.6 | 检索响应 P95 < 1.5 秒（1 万文档规模） | P0 | 压测达标 |

### FR-5 AI 问答（RAG）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-5.1 | 基于检索结果生成答案，流式输出 | P0 | 首字节 < 3 秒 |
| FR-5.2 | **答案必须带引用**，标注来源文档名 + 片段 + 可跳转 | P0 | 每个事实性论断可追溯到具体来源 |
| FR-5.3 | **检索无结果时明确拒答**，禁止编造 | P0 | 库外问题回复"知识库中未找到相关内容"，不臆造 |
| FR-5.4 | 引用 `draft` 等级知识时明确标注"该内容未经质量验证" | P0 | 标注可见 |
| FR-5.5 | 机密文档默认不入上下文，需显式开关且记审计 | P0 | 默认关闭 |
| FR-5.6 | 多轮对话，保留会话上下文 | P1 | 支持追问 |
| FR-5.7 | 答案反馈（有用 / 无用 / 有误），沉淀为评测集素材 | P1 | 反馈可导出 |

### FR-6 检索质量评测（支撑"准确率 ≥ 90%"）

| 编号 | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-6.1 | 评测集管理：问题 + 期望命中文档 ID（金标准），可导入导出 | P0 | 支持 CSV/JSON 维护 |
| FR-6.2 | 一键运行评测，输出 Recall@K、MRR、命中率 | P0 | 结果可复现、可存档 |
| FR-6.3 | 评测历史留档，可对比不同配置下的效果 | P0 | 支持"改了参数后是升是降"的判断 |
| FR-6.4 | 用户反馈数据可转化为评测用例 | P1 | 一键从反馈生成用例 |

> **这是"10 月底准确率 ≥ 90%"能否交差的唯一客观依据。没有它，KPI 是口号。**

## 6. 非功能需求（NFR）—— 逐条对应你提的八个"可"

### NFR-1 可用

| 项 | 指标 | 实现手段 |
|---|---|---|
| 检索响应 | P95 < 1.5s @ 1万文档 | SQLite FTS5 + 内存向量索引 |
| 问答首字节 | < 3s | 流式输出 + 检索并行 |
| 服务可用性 | ≥ 99%（内网工作时段） | 单机 + Docker restart:always + 健康检查 |
| 优雅降级 | 模型不可用时检索仍工作 | FR-9.4 |
| 数据规模 | 支撑 5 万文档 / 200 万切片 | 索引分片 + 分页 |

### NFR-2 可维护

- **分层架构**：`providers`（模型）/ `ingest`（入库）/ `search`（检索）/ `api`（接口）/ `web`（界面）职责单一，可独立替换
- **全中文逐行注释**（团队 .NET 背景，降低 Python 上手成本）—— 硬性要求
- **配置外置**：所有可变参数走 `.env` + `config.py`，不散落硬编码
- **结构化日志**：分级输出，问题可定位
- **零重型依赖**：不引入 LangChain 等黑盒框架，检索链路完全可读可调
- **数据库迁移**：schema 变更走版本化迁移脚本

### NFR-3 可落地

- **8 月底可上线**：一期聚焦 P0，砍掉一切非必要
- **单机 Docker Compose 一键部署**，无需 K8s、无需独立向量数据库
- **本地先跑通**（Mac）→ 验证 → 打包上内网 192.168.0.61，路径一致
- **初始化脚本**：一条命令建库、建管理员、灌示例数据
- **迁移成本低**：全部数据在 `data/` 目录，拷走即迁移

### NFR-4 可扩展

| 扩展方向 | 预留机制 |
|---|---|
| 换模型（云 → 私有化） | Provider 抽象接口，配置驱动 |
| 换向量库（内存 → Milvus） | VectorStore 抽象接口 |
| 加文档格式 | Parser 注册表，新增一个解析器函数即可 |
| 加分类 | 分类表配置化，不硬编码 |
| 上层场景接入 | 开放 REST API |
| 数据量增长 | SQLite → PostgreSQL 的 DAO 层隔离 |

### NFR-5 可控

- **成本可控**：显示 token 消耗与调用次数；embedding 结果缓存，同内容不重复计算
- **行为可控**：AI 只基于检索结果回答，无检索结果则拒答（不放任自由生成）
- **范围可控**：机密文档默认隔离于 AI 上下文之外
- **灰度可控**：按部门、按功能开关逐步放开
- **速率可控**：API 调用频率限制

### NFR-6 可审计

- 11 类事件全链路留痕（FR-11）
- 审计日志**只增不改**，应用层无删除路径
- 每个 AI 答案可回溯到具体知识片段（引用溯源）
- 文档全生命周期留痕：谁上传、谁审核、谁修改、谁下架
- 支持导出，满足合规检查

### NFR-7 安全可靠

| 层面 | 措施 |
|---|---|
| 认证 | PBKDF2-SHA256 加盐哈希，≥200k 迭代 |
| 会话 | HttpOnly Cookie，签名，超时失效 |
| 注入 | 全部 SQL 参数化，零字符串拼接 |
| 上传 | 格式白名单 + 大小限制 + 文件名消毒 + 内容哈希去重 |
| 越权 | 权限检查在**数据层**执行，非前端隐藏 |
| XSS | 模板自动转义，用户内容不 innerHTML 直出 |
| 密钥 | API Key 走环境变量，不入代码库；`.env` 在 `.gitignore` |
| 数据 | 本地存储，不出内网（内网部署后）；每日自动备份 SQLite |
| 可靠 | 事务保证入库原子性；解析失败不污染索引；异常有兜底 |

### NFR-8 易用

- **三秒上手**：进来就是搜索框，不需要培训
- **上传 ≤ 3 步**：选文件 → 填元数据（智能预填）→ 提交
- **元数据智能预填**：从文件名、文档内容自动推断标题、分类、日期，人工只需确认
- **批量优先**：部门联络人一次传一批，不折磨人
- **错误提示说人话**：不是"Error 500"，而是"第 3 份文档缺少『生效日期』，请补充后重新提交"
- **深色主题**，长时间使用不刺眼
- **零结果不留白**：给出改写建议与相近结果

## 8. 技术架构

```
┌──────────────────────────────────────────────────┐
│  Web UI（检索 / 问答 / 上传 / 审核 / 看板 / 管理）  │
├──────────────────────────────────────────────────┤
│  REST API（会话鉴权 + API Key 鉴权 + 审计埋点）    │
├──────────────────────────────────────────────────┤
│  业务层                                           │
│  ├─ ingest   解析 → 校验 → 切片 → 向量化 → 入库    │
│  ├─ search   BM25 ∥ 向量 → RRF 融合 → 权限过滤     │
│  ├─ rag      检索 → 组装上下文 → LLM → 引用溯源     │
│  ├─ lifecycle 版本 / 复审 / 下架                   │
│  └─ eval     评测集 → 跑分 → 留档对比              │
├──────────────────────────────────────────────────┤
│  Provider 适配层（可插拔）                         │
│  ├─ LLM:       DeepSeek │ OpenAI兼容 │ Ollama      │
│  └─ Embedding: SiliconFlow │ OpenAI兼容 │ Ollama   │
├──────────────────────────────────────────────────┤
│  存储层                                           │
│  ├─ SQLite（业务数据 + FTS5 全文索引 + 审计）       │
│  ├─ 向量索引（float32 blob + 内存加载）             │
│  └─ 文件存储（data/uploads）                       │
└──────────────────────────────────────────────────┘
```

**技术选型理由**

| 选型 | 理由 | 未来升级路径 |
|---|---|---|
| Python + Flask | 团队已有 Flask 项目经验（智采日报），运维一致 | — |
| SQLite + FTS5 | 零运维、单文件备份、内网友好；万级文档性能充足 | → PostgreSQL + pgvector |
| numpy 向量暴力检索 | 10 万切片内毫秒级；无外部依赖 | → Milvus / Qdrant |
| jieba 中文分词 | FTS5 对中文需分词才有效，jieba 是成熟方案 | — |
| RRF 融合 | 无需训练、无需调参、鲁棒性强 | → 加 reranker 模型 |
| 不用 LangChain | 黑盒难调试；检索链路必须可读可控 | — |

### 9.2 关键 KPI 的技术定义（避免验收扯皮）

> **"AI 检索查询准确率 ≥ 90%"** 的精确定义：
>
> 在覆盖六大知识域、不少于 100 条、由业务方确认的评测集上，
> **Recall@5 ≥ 90%** —— 即对于 90% 以上的测试问题，正确答案所在文档出现在检索返回的前 5 条结果中。
>
> 评测集须满足：
> - 每个一级分类不少于 10 题
> - 包含至少 30% 的"同义改写型"问题（考察语义检索能力）
> - 包含至少 10% 的"库外问题"（考察正确拒答能力，拒答正确计为通过）
> - 由业务方（庄金冬 + 部门联络人）确认金标准，技术方不自评自证
